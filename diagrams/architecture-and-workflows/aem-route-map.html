A developer builds features. A platform engineer keeps environments running. A TSE sits between the customer and Adobe engineering: a customer opens a case saying "something is broken", and the TSE must work out which layer is broken, why, and what the customer or Adobe must change. Architecture: the stops on the route

AEM as a Cloud Service (AEMaaCS) is AEM run by Adobe on Kubernetes. You never log into a server. Each environment (dev, stage, prod, RDE) has several services (also called tiers):

TierWho uses itKey facts
AuthorContent authors, approvers, adminsWhere content is created, workflows run, assets are processed. Runs as a cluster of pods sharing one repository (document store). Behind login (Adobe IMS).
PublishWebsite visitorsSeveral pods, each with its own copy of published content. Read-mostly. Each pod has Apache + Dispatcher in front of it.
PreviewBusiness reviewersA separate publish-like tier. Content is published to Preview first for review, without going live. Your "preview to publish" workflow used this. Your experience
DispatcherSits in front of Publish/PreviewApache module: allows or blocks requests (filters), caches responses, rewrites URLs. You deploy its config from Git.
CDNAll public trafficAdobe-managed CDN (Fastly). Terminates SSL, caches, applies IP allowlists and traffic rules, serves custom domains.
Cloud ManagerDevelopers, DevOpsSelf-service portal + CI/CD: pipelines, environments, domains, SSL certificates, IP allowlists, logs, environment variables.

The software stack inside one AEM instance

Every AEM instance (author or publish) is the same layered Java application. Knowing the layers tells you which kind of log line or error belongs to which part.

The repository: JCR, Oak, and where everything lives

Everything in AEM is stored as a tree of nodes. A node has a name, a type (jcr:primaryType, such as cq:Page, dam:Asset, nt:unstructured) and properties. A page is a cq:Page node with a jcr:content child that holds its components. JCR is the standard (Java Content Repository API); Oak is Adobe's/Apache's implementation of it.

PathHoldsMutable in cloud?
/libsAdobe product code. Never edit.No
/appsYour project code: components, overlays, OSGi configsNo (pipeline only)
/confEditable templates, policies, workflow models, Cloud configurationsYes
/contentPages (/content/<site>), assets (/content/dam), experience fragments, formsYes
/varRuntime data: workflow instances and runtime models (/var/workflow), audit logsYes
/homeUsers and groups (/home/users, /home/groups)Yes
/oak:indexSearch index definitionsVia pipeline only

Storage: two kinds of node store Learn as theory

  • Segment store (TarMK): files on local disk; fast; single instance. Used by each publish pod in the cloud (and by most on-prem installs). Needs "online revision cleanup" (compaction) on-prem.
  • Document store (MongoMK): nodes stored in a database, so several author pods can share one repository. Used by cloud Author.
  • Binaries (images, PDFs) live in a separate blob store (cloud object storage), not inside the node tree.

Mutable vs immutable content packages

A cloud project builds separate packages: ui.apps (immutable code to /apps), ui.config (OSGi configs and Repoinit), ui.content (mutable starter content to /conf, /content). Putting mutable content in the immutable package, or the reverse, makes the build or deploy fail. This is a common customer case.

Repoinit: creating repository structure as code

Because you cannot click to create service users, paths or namespaces on a cloud tier, you declare them in a Repoinit script, deployed as an OSGi config (org.apache.sling.jcr.repoinit.RepositoryInitializer~name.cfg.json). It runs on every start and is idempotent (safe to re-run).

register namespace (mysite) http://example.com/mysite/1.0
create service user mysite-content-reader
create path /conf/mysite(sling:Folder)
set ACL for mysite-content-reader
    allow jcr:read on /content/mysite
end

Illustrative script; names are examples, not your project's real values.

Your experience: namespace issues across RDE, QA, STAGE, PRODDuring on-prem to cloud migration, content used a namespace that did not exist on the cloud repository. A node property such as mysite:something fails to save if the mysite prefix is not registered. You fixed it by registering the namespace through Repoinit, so every environment got it from code. Connect it to the concept: in the cloud, repository structure is code, and every environment must get it from the same pipeline.

Sling and OSGi: how a URL becomes a page

Sling does not map URLs to Java classes. It maps a URL to a resource (a node), then reads the node's sling:resourceType to find the script (HTL) that renders it. Learn to split any AEM URL into its parts:

/content/mysite/xx/en/contactresource path.teaser.mobileselectors.htmlextension/extra/infosuffix?q=1query (ignored by cache)
  1. Resource resolution: Sling finds the longest path that exists as a node, applying mappings (/etc/map, resource resolver factory config) that shorten or rewrite paths.
  2. Read the resource type: e.g. mysite/components/page. If no script is found, Sling follows sling:resourceSuperType (inheritance), e.g. to core/wcm/components/page/v3/page.
  3. Script selection: picks the most specific script matching selectors, extension and HTTP method (teaser.mobile.html beats html).
  4. Render: the HTL script calls Sling Models (Java) for data, includes child components, outputs HTML.
  5. Filters and response: Sling filters run around the request (authentication, caching headers, custom filters).

Why this matters for support: a 404 from AEM itself means "no resource at that path" (or no read permission, since unreadable looks like missing). A 500 usually means the script or Sling Model threw an exception (see error.log). Wrong extension or missing .html often hits a different script or a filter rule.

Your experience: preview links not navigating correctlyLinks on a page in the cloud preview environment went to the wrong place because the URL had no .html extension. You added a dispatcher rewrite rule to append .html for the site's content paths. The concept: Sling needs the extension to choose the HTML rendering, and the dispatcher's rewrites run before the request reaches Sling, so they are the right place for URL shaping on publish/preview.

OSGi in one minute

  • Bundle: a JAR with metadata; states installed, resolved, active. A bundle stuck in "installed" means a missing dependency (an import no other bundle exports).
  • Component / service: a Java class managed by OSGi (@Component), can offer a service and depend on others (@Reference). If a required reference is missing, the component is "unsatisfied" and its feature silently does nothing.
  • Configuration: values for a component, stored as .cfg.json files in /apps/<project>/osgiconfig/config.<runmode>.
  • Run modes: pick configs per tier and environment: config.author, config.publish, config.author.prod, config.stage, config.dev.
  • Environment variables and secrets: in the cloud, put environment-specific values in Cloud Manager and reference them: "$[env:SMTP_HOST;default=localhost]", "$[secret:SMTP_PASSWORD]". Secrets never go in Git.
  • Where to check in the cloud: Developer Console (from Cloud Manager) shows bundle status, components, configurations, and lets you run query explain. Learn as theory if you have not opened it.
Your experience: the SMTP token that expiredEmails stopped because the token AEM used to authenticate with the mail server expired after about 90 days of inactivity. You logged in as the mail service account, generated a new token, updated AEM's mail configuration, and asked the team to refresh it monthly. The concepts underneath: the Day CQ Mail Service OSGi config sends email; modern providers (for example Microsoft 365) require OAuth2 instead of a password, which uses an access token plus a refresh token, and Microsoft's refresh tokens expire after a period of inactivity (90 days by default). A durable fix stores the value as a Cloud Manager secret variable, so rotating it does not need a code change. Confirm for yourself which provider and which config your project used before describing it in detail.
Theory to add: outbound email from the cloudAEMaaCS blocks outbound traffic on non-HTTP ports by default. To send SMTP, a program enables advanced networking (flexible port egress or dedicated egress IP) and configures port forwarding; the mail config then uses the proxy host Adobe provides (AEM_PROXY_HOST). "Email stopped working" cases usually come down to: networking config, credentials/token expiry, the OSGi mail config, or the mail server rejecting the sender.

Dispatcher: the gatekeeper and the cache

Dispatcher is an Apache HTTP Server module. It has three jobs: security (only allow URLs you expect), caching (save rendered pages as files so Publish does less work) and URL handling (rewrites, redirects, virtual hosts for multiple domains).

The configuration files you need to recognise

File / sectionPurpose
conf.d/available_vhosts/*.vhostApache virtual hosts: which domain names (ServerName/ServerAlias) this config answers. Domain mapping across environments starts here.
conf.d/rewrites/*.rulesmod_rewrite: redirects (301/302), short URLs, appending .html, vanity paths.
conf.dispatcher.d/filters/*.any/filter: allow/deny by method, path, selectors, extension, suffix. Start from deny-all, then allow.
conf.dispatcher.d/cache/*.any/cache /rules (what to cache), /invalidate (which files become stale on publish), /ignoreUrlParams.
conf.dispatcher.d/clientheadersWhich request headers are passed to Publish.
conf.dispatcher.d/farmsA farm ties vhosts, filters, cache and renders (the Publish backend) together.
statfileslevelHow deep .stat files go. On publish, files under that folder become stale ("invalidated"), so the next request fetches a fresh copy.

Filter rule anatomy

/0100 { /type "allow" /path "/content/mysite/*" /extension '(html|json|css|js|png|jpg|jpeg|gif|svg|pdf)' }
/0101 { /type "deny"  /selectors '(feed|rss|infinity|tidy|sysview|docview|query|[0-9-]+)' }

Regex in single quotes is case-sensitive. jpg does not match JPG. Later rules override earlier ones, so order matters.

Your experience: images and .xlsx giving 404 on the live siteYou confirmed the image existed in author and directly on publish, so the content was fine. The images had an uppercase .JPG extension, which the filter's extension list did not allow, so dispatcher denied them and returned 404. You allowed it in the filter, and later did the same for a reported .xlsx case. This is a model troubleshooting story: prove which layer has the problem before changing anything. A cleaner long-term fix is a case-insensitive pattern such as '(?i)(jpg|jpeg|png)' if your dispatcher version supports it, or listing both cases.
Your experience: dispatcher domain mapping across RDE / QA / STAGE / PRODEach environment answers different host names, so vhosts and rewrite rules must map each domain to the right content root (for example www.site.com to /content/mysite/xx). Environment-specific host names are usually handled with variables (for example ${ENVIRONMENT_TYPE} or custom variables in conf.d/variables) so one config works in all environments.

Cloud-specific dispatcher facts Close to your work

  • The config lives in the project's dispatcher Maven module and is deployed by a full-stack or web-tier config pipeline.
  • Some files are immutable (provided by Adobe); you can only add your own includes. The build runs a validator that fails the pipeline on forbidden directives.
  • Test locally with the Dispatcher SDK (Docker) and validate.sh before pushing. Learn as theory if you have not used it.
  • Invalidation happens automatically when content is published; you do not configure flush agents in the cloud.

CDN, domains, SSL and network access

Every AEMaaCS environment comes with an Adobe-managed CDN. Requests to the live site arrive there first. To understand most "site not reachable" cases you need four ideas: DNS, SSL certificates, caching and IP-based access.

Going live with a custom domain

  1. Add the SSL certificate in Cloud Manager (customer-managed certificate, or an Adobe-managed DV certificate). The certificate must cover the domain name, including www if used.
  2. Add the domain name in Cloud Manager and verify ownership (a TXT record).
  3. Map the domain to the environment and tier (publish or preview).
  4. Point DNS: the customer's network team creates a CNAME record to Adobe's CDN host (cdn.adobeaemcloud.com); apex domains use A records Adobe documents.
  5. Dispatcher: the vhost must answer that host name, and rewrites must map it to the right content root.
Your experienceYou updated SSL certificates in Cloud Manager, worked with the network team to update internal and external DNS records to point at Adobe's CDN, configured domain mapping in Cloud Manager, and set up matching dispatcher config. That is the full go-live chain above; you can explain each step from experience.

IP allowlists and CIDR

Cloud Manager can restrict an environment's tier (author, publish, preview) to listed IP ranges. Ranges are written in CIDR notation: 203.0.113.0/24 means the first 24 bits are fixed, so 256 addresses (203.0.113.0 to .255). /32 is one address. A request from an address outside the list is blocked at the CDN with 403, before AEM is involved.

Your experience: authors in one region getting 403 on prod authorYou first checked their AEM access (fine), checked the users had migrated to the cloud, then found in the logs that their requests came from IP addresses outside the allowlist. You got the office's CIDR range, added it to the Cloud Manager IP allowlist and had the users verify. Lesson for the interview: a 403 for one group of users, while others are fine, points to something that differs between them: permissions or network location. You checked both.

CDN caching Close to your work

  • The CDN obeys Cache-Control and Surrogate-Control headers set by AEM or dispatcher. If none are set, Adobe applies a short default TTL for HTML/JSON (a few minutes).
  • So after a publish, the dispatcher copy is invalidated immediately, but the CDN may keep the old page until its TTL ends. "I published but the site still shows old content" is often this.
  • Read headers with curl -I https://www.site.com/page.html: look at Age, Cache-Control, X-Cache (HIT/MISS).
  • Purge: possible via the CDN purge API with a purge key configured through the config pipeline. Learn as theory

Newer CDN features Learn as theory

  • Config pipeline with a cdn.yaml: traffic filter rules (block paths, countries, rate limits), WAF rules, request/response transformations, redirects at the edge, origin selectors.
  • Customer-managed CDN (BYOCDN) in front of Adobe's: the customer's CDN must send the expected host header and a secret header (X-AEM-Edge-Key), otherwise Adobe's CDN rejects or misroutes the request.
  • Log forwarding of CDN and AEM logs to Splunk, Datadog and similar.

In the cloud this uses Sling Content Distribution: Author packages the content and sends it to an Adobe pipeline service; every publish pod picks it up and imports it. When publishing fails: what to check

Users, groups and permissions

Access in AEMaaCS has two layers. Mixing them up is the most common reason people misdiagnose a 403.

How AEM decides a permission

  • A permission is an access control entry (ACE): principal (user or group) + allow/deny + privileges + path, stored in a rep:policy node.
  • Entries inherit down the tree. An entry on a deeper path overrides the parent's for that subtree.
  • At the same node, entries for the user take precedence over entries for groups; among groups, the order in the list matters.
  • everyone has read on many product paths; a deny for everyone affects all users, so be careful.
  • Best practice: grant to groups, never to individual users; keep a group per role and site (e.g. mysite-xx-authors, mysite-xx-approvers).
  • Tools: Tools → Security → Permissions (view effective permissions, test a privilege for a user on a path); Groups; Users. In code: Repoinit set ACL.
  • Closed User Groups (CUG) restrict who can see pages on Publish (login-protected areas). Learn as theory
  • Service users: technical users for code (via ServiceUserMapper config), never admin sessions. Created with Repoinit. Close to your work
Your experience: country authors and approversYou created users and groups for country-specific authors and approvers for all the platform's sites, through Cloud Manager / Admin Console and AEM groups. Explain the model you used: product profile for login, then site- and role-specific AEM groups with ACLs on each country's content tree, approvers being the members of a workflow participant group.
Check your own detailBe ready to say exactly which part you did in Admin Console (adding users to product profiles) and which part in AEM (groups and ACLs). If one of them was done by another team, say so.

Workflows

A workflow automates a process: approval before publish, asset processing, translation. It has a model (the design), launchers (start automatically on an event) and instances (each running copy).

PieceWhere it livesNotes

Typical workflow problems

  • Instance stuck or "failed": check the instance history and error.log for the step's exception; retry the step from the Failures view.
  • Launcher not firing: wrong path glob, node type, run mode, or the launcher is disabled.
  • Approver does not see the task: they are not in the participant group, or the inbox filter hides it.
  • Too many instances: configure Workflow Purge (scheduled maintenance task). Transient workflows avoid storing history. Learn as theory

Components, templates and forms

Core Components and versioning

Adobe's Core Components (Page, Title, Text, Image, List, Teaser, Container, Form...) are production-ready building blocks. Projects use proxy components: a component in /apps/<project> with sling:resourceSuperType pointing at a specific core version, e.g. core/wcm/components/list/v4/list. Upgrading from v3 to v4 means changing that super type and checking that dialogs, HTL and CSS still work.

Delegation pattern

To change one value without copying the whole core component, a custom Sling Model implements the same interface and delegates everything else to the core model (@Self @Via(type = ResourceSuperType.class)). Only the changed method has new logic.

Your experience: List component "Display as Teaser"Selecting "Display as Teaser" in the List did not work as expected. You updated the teaser delegate property (the List's policy/property that names which Teaser component renders each item) and upgraded the List from v3 to v4. The concepts: proxy components, versioned core components, and policies that configure a component per template.

Editable templates and policies

  • Templates live in /conf/<site>/settings/wcm/templates; authors with template-author rights edit them.
  • Structure (locked parts), initial content, layout (responsive grid), policies (allowed components, styles, default settings per container).
  • Style System lets authors pick CSS classes defined in a policy.

Client libraries

Folders of CSS/JS with categories; pages include them by category. On publish, they are served through /etc.clientlibs/ (a proxy path), so dispatcher filters must allow /etc.clientlibs/*. A page without styling on publish but fine on author: suspect a filter blocking /etc.clientlibs or a missing allowProxy flag.

Isolation technique

  1. Reproduce with curl -v or browser dev tools; note status, headers (Age, X-Cache, Cache-Control), time.
  2. Compare the custom domain with the environment's default URL (publish-p<program>-e<env>.adobeaemcloud.com): if only the custom domain fails, look at DNS, SSL, domain mapping or vhost.
  3. Compare author vs publish vs preview: content or permission vs delivery.
  4. Add a cache-busting query string (?nocache=1): if it works, the cached copy is the problem.
  5. Check the same request in CDN log → dispatcher log → AEM request/error log; the first layer that shows the error status, with nothing behind it, is where it was produced.

Performance

A fast AEM site serves almost everything from cache. Performance problems usually come from (1) poor cache hit ratio, (2) a page that is expensive to render, (3) slow repository queries, or (4) slow external calls.

Cache hit ratio

Check CDN and dispatcher cache status. Query strings, personalised headers, no-cache headers and too-wide invalidation (low statfileslevel) all reduce hits.

Render cost

Many nested containers and components, heavy Sling Models, many includes. Each component is a separate include with its own processing.

Queries and indexes

A query without a matching Oak index traverses the repository; logs warn "Traversed N nodes". Fix with a custom index (deployed via pipeline, named like damAssetLucene-8-custom-1) or rewrite the query. Use Query Explain in Developer Console. Learn as theory

External calls

HTTP calls inside components without timeouts or caching block render threads; under load this becomes 503/504.

Your experience: a regional team 503 after publishing a pageYou checked logs and confirmed the page was published, then saw in publish that it was not loading, with far more calls than expected. The page used an excessive number of containers. You removed unnecessary containers, re-authored the page with proper styling and republished, then gave authors guidance to use the minimum number of containers. The concepts: render cost per component, request timeouts producing 503, and prevention through authoring guidelines (template policies can also limit allowed components).

The troubleshooting method

Use the same seven steps for every case. Your task log already follows them; naming them makes your explanations sound structured.

  1. Scope: which environment, tier, URL, users, since when, what changed (deployment, publish, DNS, certificate, migration)?
  2. Impact: production down, part of users, one page? Sets priority and how often you update the customer.
  3. Reproduce: same request yourself; author vs publish vs preview; custom domain vs default domain.
  4. Isolate the layer: walk the route map from the outside in: client → DNS → CDN → Dispatcher → Publish → code/content → repository.
  5. Evidence: logs for that time and URL, headers, configs in Git, pipeline history, Admin Console.
  6. Fix or workaround: smallest safe change first; rollback is a valid fix (you reverted after the ingestion issue). Verify with the affected users.
  7. Root cause and prevention: why it happened, why it was not caught, what stops it happening again (validation, review, monitoring, documentation).

Communicating like a TSE

  • First reply: acknowledge, restate the problem, say what you need (URL, time, request ID, screenshots, recent changes).
  • Updates: what you checked, what you found, what is next, when you will update.
  • Explain the cause in the customer's terms, then the technical detail.
  • Be clear when the fix belongs to the customer (their dispatcher config, their code) and when it is an Adobe issue to escalate with complete evidence.
